# World Language Graph — Architecture Design for ELSEWHERE (2026-11-26)

**Status.** Design only. This document registers nothing, builds nothing, populates nothing, spawns no ELSEWHERE instance, and moves no standing, verdict, tally, or baseline pin. It specifies an architecture that the owner may later commission as its own study. Until then, the World Language Graph is a filed proposal.

**Governing inputs.** The design follows the ELSEWHERE Framework Specification, Version 1 (Spec 106, `specs/106-elsewhere-world-model-templates/framework.md`, read at repository head `8465d9eb7dbfcd946b7734a1af8bee1f84d06d7f`), the three Spec 106 baseline templates, and the Active Decipherment Design of 2026-11-26. The framework rules that bind this design are not paraphrased loosely:

- every premise carries exactly one kind label — **(F)** floor fact, **(K)** period knowledge with a named source, or **(H)** hypothesis declared openly;
- an UNSOURCED line may appear only as an (H), where it names a variable and is never a usable premise;
- an assumption enters only as a labelled axiom of a declared instance, never inside a derivation, dataset, translation, or checker — the no-smuggling rule;
- evidence is not an axiom, and an instance is scored against a declared evidence set at registered contact points;
- a baseline is never itself an instance and is never scored;
- retired records and filed verdicts are not edited in place; change is made by a new version, a superseding record, or an appended correction;
- papers and reports present results and cite the history ledger; the story of decisions, failures, and corrections lives in the ledger.

The three existing baselines are the design's worked reference point. Their Domains 2–8 contain 88 Indus axioms (F 4 / K 74 / H 10; axiom-line SHA-256 `eb0e1d6218fadf8eed06c78eeb92979163ebb37b1206eb3d151c9c0d23b501e6`), 71 Eteocypriot axioms (F 3 / K 58 / H 10; `fca1cc8a238631b0c6df8b2901daa5e84dc4cb2387dcdad560285c6e95beec4f`), and 76 Meroitic axioms (F 4 / K 62 / H 10; current version-2 pin `ecabd227f7e767a3a740ece3b355d8620db476b89ac482d7a8386b483a97f4f2`). Domain 1 in each is carried by reference to Spec 105 rather than duplicated. The graph must extend that discipline to a much larger evidence surface without weakening it.

## Architecture at a glance

The World Language Graph is **not a picture and not a single database table**. It is a versioned, source-bound assertion system with a graph-shaped canonical store, generated indexes, and replaceable renderings. The picture is a view. The graph of record is the set of versioned assertions underneath it.

```text
SOURCE REGISTRY
  books, papers, catalogues, corpus editions, datasets, program records
  each source opened, identified, versioned, and access-labelled
                │
                ▼
ASSERTION EXTRACTION AND VERIFICATION
  field-level and edge-level claims, each with evidence class,
  source locator, temporal/spatial scope, reviewer state
                │
                ▼
CANONICAL GRAPH RELEASE  ─────────────►  GAP REGISTER
  language nodes · script nodes          one register entry for every
  relationship assertions · context      undeciphered script and every
  assertions · provenance                not-understood language
                │                                   │
                ├──────────────► SPHERICAL / TEMPORAL VIEWS
                │                 generated, reproducible, non-evidentiary
                │
                └──────────────► ELSEWHERE AXIOM EXPORTS
                                  reviewed candidate axiom packs;
                                  adopted only by baseline amendment
```

### Canonical form

The source of truth is a set of append-only, text-diffable record streams in a versioned graph package:

| Stream | Contents |
|---|---|
| `sources.jsonl` | One record per source actually opened, with bibliographic identity, version, access route, licence or access constraint, and the date opened. |
| `nodes.jsonl` | Language and script nodes. A node carries identity and links to assertions; it does not silently absorb contested claims as facts. |
| `edges.jsonl` | Relationship assertions between nodes or between a node and an explicitly typed context entity. Competing edges remain separate records. |
| `assertions.jsonl` | Field-level sourced assertions for values that are not relationships: attestation, geography, corpus, status assessments, and covariate blocks. |
| `gaps.jsonl` | Gap-register entries, each pointing to exactly one target language or script node and to the hypothesis edges that concern it. |
| `releases.jsonl` | Immutable graph releases: record counts, stream hashes, source-manifest hash, schema version, and the audit outputs that admitted the release. |
| `baseline-links.jsonl` | The mapping from graph assertions to baseline axioms that have adopted them, by baseline, template version, axiom ID, and graph assertion ID. |

Generated SQLite, graph-database, search, and geospatial indexes may be built from a release for speed. They are replicas, never the record. If an index and the canonical stream disagree, the stream governs and the index is rebuilt.

### Identity rule

Names are labels, not identities. Every node, edge, assertion, source, gap, and release receives a persistent opaque ID at creation. A later change of preferred name, spelling, transliteration, or catalogue cross-reference changes an alias or crosswalk record, not the ID. A merge or split is a ledgered identity event that retires the old mapping into a supersession record; IDs are never recycled.

### The central separation

Four things that ordinary language maps habitually blur are kept separate throughout:

1. **A language is not its script.** A language node and a script node are different objects, joined by a time-scoped `WRITES` relation.
2. **A population is not a language.** Genetic movement is recorded on population or community context entities and never converted, by data model or by rendering, into language descent.
3. **A placement estimate is not a node fact.** Family placement lives in sourced placement assertions and hypothesis edges. A node has a set of placement assertions, including possibly none; it does not have an unqualified `family` string.
4. **A view is not evidence.** Coordinates, arcs, colours, animation, and visual clustering are rendering choices over a release. They cannot create, strengthen, or weaken an assertion.

## 1. Node schema

### 1.1 Node kinds

The canonical graph has two primary node kinds:

- **`LanguageNode`** — a linguistic system, whether living, historically attested, reconstructed, or inferred from traces.
- **`ScriptNode`** — a writing system, whether living, historical, deciphered, partly deciphered, or undeciphered.

A third record type, **`GapNode`**, is an epistemic overlay defined in §4. It points to a language or script node and records what is missing. It is never a substitute for the target node and never a claim that a separate language or script exists.

Auxiliary **context entities** may be referenced by covariate assertions and population-movement edges: named regions, sites, polities, religious institutions or traditions, cultural complexes, archaeological cultures, and population samples or communities. A context entity is not promoted to a language merely because a source uses the same name for both. Where a historical label is used for a people, a polity, a culture, and a language, the records are separate and explicitly cross-linked as labels, not merged as objects.

### 1.2 Language-node subtypes

Every `LanguageNode` carries exactly one subtype:

| Subtype | Meaning | Minimum identity basis |
|---|---|---|
| `ATTESTED` | A language directly attested in speech records, texts, transcriptions, wordlists, or reliable documentation. | At least one sourced attestation assertion. |
| `RECONSTRUCTED` | A proto-language or reconstructed ancestor posited by a stated comparative method. | A reconstruction source and at least one sourced descendant or placement assertion. It has no direct attestation window of its own in the same sense as an attested language. |
| `INFERRED_UNKNOWN` | An unattested language inferred from substrate vocabulary, place-names, loanword strata, contact effects, or another named trace. | At least one sourced inference-basis assertion. The node names an inference, not a discovered speech community. |
| `FAMILY_OR_CLADE` | A named grouping node used as the target of placement assertions and the parent in genetic-descent assertions. | A classification source. A family node is a taxonomic object, not a claim that the family was ever one uniform spoken language. |
| `DOCUMENTATION_UNIT` | A deliberately narrow unit used where sources disagree about whether varieties are one language, several languages, or a dialect chain. | A scope note naming the catalogue or study whose unit is being represented. This prevents a database convenience from becoming a linguistic claim. |

A node may be re-subtyped only by a versioned correction that explains the identity error or the change in the underlying scholarship. Re-subtyping does not rewrite earlier releases.

### 1.3 Script-node subtypes

Every `ScriptNode` carries exactly one subtype:

| Subtype | Meaning |
|---|---|
| `ATTESTED` | A script directly attested on surviving carriers or in reliable reproductions. |
| `RECONSTRUCTED` | A script stage or ancestral script form reconstructed from descendant scripts and stated evidence. |
| `INFERRED_UNKNOWN` | A writing system inferred from traces or reports but not directly available in an adequate corpus. This subtype is exceptional and requires the inference basis to be stated on the node. |
| `SIGN_LIST_UNIT` | A bounded sign-list or corpus unit used where the unity of the underlying script is itself disputed. The unit represents the filed corpus convention, not a settled claim that all its signs form one system. |

The Indus case shows why the last subtype matters: a corpus convention must be representable without silently deciding that every sign in the convention belongs to one unitary writing system. The active decipherment queue already treats the unitary-system reading as a testable hypothesis rather than a premise.

### 1.4 The universal provenance wrapper

No substantive field is a bare scalar. Each field value is either:

- an **assertion reference** to a record in `assertions.jsonl`; or
- the explicit state `UNSOURCED`, permitted only where the field is being used to name an open variable in the ELSEWHERE (H) sense; or
- the explicit state `NOT_APPLICABLE`, with a reason; or
- the explicit state `UNKNOWN`, meaning the population process looked and did not establish a value.

`UNKNOWN` and `UNSOURCED` are not synonyms. `UNKNOWN` is a result of a recorded search. `UNSOURCED` is the framework flag: no source supports the line, so it may exist only as an (H) variable and may not be consumed as a premise.

Every assertion record carries:

| Field | Requirement |
|---|---|
| `assertion_id` | Persistent opaque ID. |
| `subject_id` | Node, edge, gap, or context entity the assertion is about. |
| `field` | Controlled field name. |
| `value` | The value in the field's declared type; ranges remain ranges and are never collapsed to a point for storage. |
| `evidence_class` | Exactly one of `F`, `K`, or `H`. |
| `confidence_label` | One of `SECURE`, `WELL_SUPPORTED`, `PROBABLE`, `POSSIBLE`, or `SPECULATIVE`. This is an assessment label, not a probability. |
| `source_refs` | One or more source IDs, each with a locator precise enough to re-open the passage, table, record, or dataset row. |
| `source_scope` | What the source actually covers: period, place, corpus, sample, or population. A value may not be generalised beyond this scope without a new assertion. |
| `asserted_by` | The scholar, school, catalogue, study, or program record making the assertion, where that attribution matters. |
| `extraction` | Extractor, extraction date, and the batch ID. |
| `review_state` | `UNREVIEWED`, `SOURCE_CHECKED`, `INDEPENDENTLY_CHECKED`, or `ADJUDICATED`. Only reviewed assertions may enter a graph release marked fit for baseline export. |
| `valid_scope` | Temporal, spatial, genre, register, or corpus scope in which the value is claimed. |
| `supersedes` / `superseded_by` | Links for correction without rewriting history. |
| `removal_condition` | For an (H) assertion, the observation that would withdraw it; for an (F) or (K) assertion, the record correction or stronger source that would supersede it. |

A numeric confidence score is not invented. A source's own model-based probability may be stored as a sourced value, with the model named, but the graph does not convert scholarly confidence labels into percentages.

### 1.5 Core language-node fields

| Field block | Contents and rules |
|---|---|
| Identity | `node_id`, `kind=LANGUAGE`, `subtype`, preferred label, alias assertions, catalogue cross-references, identity notes. Aliases are assertions because names themselves have histories and political or scholarly scopes. |
| Attestation window | `earliest_attestation` and `latest_attestation`, each an assertion carrying a date range, dating basis, and the attesting material. A separate `inferred_existence_interval` may be asserted for a language believed to predate or postdate its surviving record. The two intervals are never merged. For a reconstructed node, the field records the reconstruction's proposed time depth as an (H) or (K) assertion, clearly typed as inferred. |
| Documentation interval | For living or historically documented languages, the period over which documentation exists, kept distinct from the period over which the language was spoken. |
| Region | One or more geography assertions (§3): attested-use area, attested findspot set for written material, inferred homeland where one is proposed, and modern speaker distribution where applicable. No single unqualified coordinate is stored as the language's location. |
| Corpus size class | A controlled class plus any sourced exact counts behind it: `NO_DIRECT_CORPUS`, `TRACES_ONLY`, `MICRO` (fewer than 100 running tokens or only isolated forms), `SMALL` (100–9,999 tokens), `MODERATE` (10,000–999,999 tokens), `LARGE` (1,000,000 or more tokens), or `NOT_ENUMERATED`. The thresholds are a display and triage convention of this design, not a linguistic claim. Exact inscription counts, token counts, text counts, and genre proportions remain separate sourced assertions because sources count differently. |
| Understanding status | Exactly one current assessment assertion on the language-understanding scale in §1.7, with older assessments retained as superseded records. Status is an assessment about the present state of knowledge, not an intrinsic property of the language. |
| Family placement | A set of placement-assertion IDs, never a bare family string. Each assertion names a family or clade node, the evidence class, the scholar or catalogue, the basis, and the removal condition. Competing placements coexist. A node with no accepted placement carries the explicit state `PLACEMENT_UNRESOLVED`, not a guessed family. |
| Script relations | Time-scoped `WRITES` relation assertions to script nodes, each with period, region, genre or register scope, and source. A language may have several scripts concurrently or successively; a script relation for one period does not extend to all periods by default. |
| Covariate blocks | Culture, period, geography, religion, and polity blocks as defined in §1.8. Each block is a list of sourced assertions, not a set of free-text tags. |

### 1.6 Core script-node fields

| Field block | Contents and rules |
|---|---|
| Identity | `node_id`, `kind=SCRIPT`, `subtype`, preferred label, aliases, catalogue cross-references, and sign-list convention where one exists. |
| Attestation window | Earliest and latest securely attested use, each sourced and dated as a range. A separate inferred-use interval may be asserted where scholarship proposes one. |
| Region and carriers | Attested findspot and distribution assertions; carrier and medium assertions (stone, clay, metal, papyrus, parchment, wood, seal, coin, or another controlled medium vocabulary); archaeological context where sourced. |
| System description | Script type as a sourced assessment (`LOGOGRAPHIC`, `SYLLABIC`, `ALPHABETIC`, `ABUGIDA`, `ABJAD`, `MIXED`, `MIXED_OR_UNRESOLVED`, or `UNKNOWN`), directionality, sign-inventory range, segmentation behaviour, numeral subsystem, and punctuation or word-divider behaviour. Each is an assertion; an undeciphered script may carry `UNKNOWN` for most of them. |
| Corpus size class | The same controlled classes as for languages, plus separate sourced counts for carriers, inscriptions, signs or tokens, and the counting convention. For scripts, carrier count and token count answer different questions and are never substituted for one another. |
| Decipherment status | Exactly one current assessment assertion on the script scale in §1.7. Decipherment of a script does not alter the understanding status of any language it writes. |
| Language relations | Time-scoped `WRITES` assertions to language nodes. A script may write several languages; the graph must not infer that texts in one script are in one language. |
| Covariate blocks | Culture, period, geography, religion, and polity blocks (§1.8), scoped to the script's attested use rather than to every speaker of an associated language. |

### 1.7 Status scales

Status is always dated, sourced, and revisable. The scale separates the two achievements that decipherment history often conflates.

**Script decipherment scale**

| Code | Label | Meaning |
|---|---|---|
| `S0` | Attested, values unknown | Signs are recorded, but no sign value or structural reading is secure enough to read texts. |
| `S1` | Partial values or structure | Some sign values, a numeral subsystem, directionality, segmentation, or another bounded subsystem is established, but continuous texts cannot be read reliably. |
| `S2` | Substantial values, incomplete reading | Most core sign values or a productive reading method are established, with material gaps, disputed values, or genre limits remaining. |
| `S3` | Deciphered | The script's values and reading conventions are established well enough that competent specialists can transliterate newly presented texts of the attested types without inventing values ad hoc. |
| `S4` | Deciphered and text-critically mature | S3, plus stable sign lists, variant and ligature treatment, corpus editions, and encoding or reference tooling adequate for cumulative scholarship. |

**Language-understanding scale**

| Code | Label | Meaning |
|---|---|---|
| `L0` | Inferred only | No direct corpus; the node exists because traces require or permit the inference. |
| `L1` | Attested, not understood | Material exists, but no reliable lexicon or grammar can be stated beyond isolated names, loans, or formula fragments whose interpretation is not secure. |
| `L2` | Fragmentary understanding | A bounded vocabulary, formula system, name stock, or grammatical subsystem is understood, while ordinary continuous text remains largely untranslatable. |
| `L3` | Substantial but incomplete understanding | Specialists can translate substantial attested material with a working lexicon and grammar, while affiliation, parts of the lexicon, or whole genres remain unresolved. |
| `L4` | Broadly understood | The language can be read across its attested range with established reference tools; remaining questions are normal scholarly questions rather than decipherment barriers. |
| `L5` | Fully documented for the attested record | L4, plus the surviving record is comprehensively edited and the language's grammar and lexicon are stable reference knowledge. This label describes documentation of what survives, not knowledge of everything once spoken. |

The three programs illustrate why both scales are needed, using only their filed positions:

- **Indus:** the script node is undeciphered and the language node or nodes behind the corpus are not understood. The graph must also preserve the live possibility, carried in the program's hypothesis set, that the system is not linguistic writing at all; that possibility is a hypothesis about the script node's function, not a language placement.
- **Eteocypriot:** the language is attested but not understood. Its writing relation is to the Cypriot syllabary, whose values the program record treats as settled for transliteration; reading signs aloud is therefore not represented as understanding Eteocypriot.
- **Meroitic:** the script is deciphered while the language remains only fragmentarily understood and its affiliation unresolved. Any model that lets the script's S3/S4-type status bleed into the language's status is rejected by this schema.

### 1.8 Covariate blocks

Every node carries five covariate blocks. A block may be empty only by carrying an explicit `NO_ASSERTION_POPULATED` state for the current graph release; silence is not allowed to masquerade as a negative finding.

1. **Culture.** Archaeological culture or cultural complex, material assemblage, subsistence or craft associations, and cultural-contact spheres. Each value names its source and period. An archaeological culture is not equated with a language or a people.
2. **Period.** Named period labels and absolute date ranges, each with its chronological basis. Period labels are regional and may overlap; the graph stores the label's own scheme rather than forcing every culture into one global periodisation.
3. **Geography.** Attested distribution, findspots, inferred homeland proposals, environmental zone, routes, and barriers. Geography assertions follow §3's geometry typing.
4. **Religion.** Attested religious institutions, deities or cult practices named in or directly associated with the node's record, ritual genres, and temple or funerary contexts. A religion value is scoped to the evidence: a funerary formula attests a funerary context, not the whole belief system of every speaker.
5. **Polity.** Named polities, offices, administrative systems, sovereignty or dependency relations, and the period for which each held. Modern states are never projected backwards as ancient polities; a modern location field, if present for retrieval, is typed as modern geography only.

Each covariate assertion states whether it is **directly attested**, **inferred from associated material**, or **proposed by a named scholar or school**. That manner-of-support field prevents a covariate from acquiring false solidity merely by being displayed beside direct attestations.

### 1.9 Proto-language and inferred-unknown rules

A reconstructed node must carry:

- the reconstruction source and method family (for example, comparative reconstruction as characterised by the source itself);
- the daughter or member assertions that motivate it;
- its proposed time-depth and homeland only as separate sourced assertions, each with its own evidence class;
- a `NO_DIRECT_ATTESTATION` marker, so no view or export can present it as excavated or recorded.

An inferred-unknown node must carry:

- at least one `INFERENCE_BASIS` assertion naming the trace type: substrate lexicon, toponymy or hydronymy, loanword stratum, phonological or grammatical contact effect, personal-name stock, or another named trace;
- a **minimum-claim statement**: the weakest statement the inference supports, written in plain language;
- a **forbidden-inference list**: conclusions the trace does not support, such as a homeland coordinate, a family placement, a corpus size, or an ethnic identity, unless separately asserted from their own sources;
- **identity criteria**: what would justify splitting the node into two inferred languages, merging it with an attested language node, or retiring it as an artefact of a mistaken trace analysis.

An inferred-unknown node is not a parking place for every gap. If the record supports only “some unattested language was present,” the node says exactly that and no more.

### 1.10 Node acceptance rules

A node enters a released graph only when:

1. its kind and subtype are explicit;
2. its identity basis is sourced or, for an inferred node, its inference basis is sourced;
3. every populated field resolves to reviewed assertions or an explicit state;
4. its status assessment is present for its kind;
5. its family placement is represented as assertions or as `PLACEMENT_UNRESOLVED`;
6. no field has been filled by inference from a neighbouring node, a script relation, a population edge, or a rendering coordinate.

Failure of any rule quarantines the node from the release. Quarantine is a recorded population outcome, not a silent omission.

## 2. Edge schema

### 2.1 An edge is an assertion, not a decoration

Every relationship in the graph is a sourced assertion record. There is no anonymous line between two nodes. An edge that cannot name its evidence class, source, scope, and removal condition does not enter a release.

Every edge record carries:

| Field | Requirement |
|---|---|
| `edge_id` | Persistent opaque ID. |
| `predicate` | One controlled predicate from §2.2, or a structural relation from §2.3. |
| `subject_id` / `object_id` | Typed endpoints. The endpoint kinds permitted for the predicate are enforced by schema. |
| `direction` | Directed, undirected, or multi-party. Undirected and multi-party relations are stored as such; the renderer may not silently choose a direction for them. |
| `evidence_class` | Exactly one of `F`, `K`, or `H`. |
| `confidence_label` | `SECURE`, `WELL_SUPPORTED`, `PROBABLE`, `POSSIBLE`, or `SPECULATIVE`, as an assessment distinct from evidence class. |
| `source_refs` | Sources actually opened, with locators. |
| `asserted_by` | Scholar, school, catalogue, study, or program record responsible for the assertion. |
| `basis` | The kind of basis: direct attestation, comparative reconstruction, shared innovation set, loanword stratum, sign-form comparison, corpus distribution, ancient-DNA analysis, archaeological association, or another controlled basis named by the source. |
| `temporal_scope` | The interval in which the relationship is claimed. An edge without a temporal scope carries `TEMPORAL_SCOPE_UNSPECIFIED`; it is not treated as true for all time. |
| `spatial_scope` | The region or contact zone in which the relationship is claimed, where applicable. |
| `feature_scope` | For contact, borrowing, and convergence: the lexemes, sounds, constructions, signs, genres, or practices involved. A whole-language borrowing edge with no feature scope is not accepted. |
| `falsifier_or_removal_condition` | The observation, analysis, source correction, or failed prediction that would remove, narrow, or supersede the edge. “More research” is not a removal condition. |
| `status` | `ACTIVE`, `CONTESTED`, `SUPERSEDED`, or `WITHDRAWN`. Withdrawal and supersession retain the record. |
| `dependencies` | Other assertions the edge depends on, so a source correction can be impact-traced. |
| `review_state` | The same review ladder as field assertions. |

### 2.2 Historical relationship predicates

| Predicate | Endpoints and meaning | What it never means |
|---|---|---|
| `GENETIC_DESCENT` | Directed, from an ancestor, proto-language, or family/clade node to a descendant language node. It asserts descent under a stated comparative basis. | It does not assert that the descendant's script descends from the ancestor's script, that its speakers are genetic descendants of the ancestor's speakers, or that the relationship is uncontested. |
| `CONTACT_BORROWING` | Directed, from a donor language to a recipient language, with a named feature scope and period. | It does not assert genetic relationship, population replacement, or borrowing of an entire language. |
| `SCRIPT_DESCENT` | Directed, from an ancestral script to a derived script, on a stated sign-form, structural, or historical basis. | It does not assert descent of the languages written in those scripts. |
| `SCRIPT_BORROWING` | Directed, from a source script tradition to a derived or adapted script, where the historical claim is borrowing or adaptation of the writing system rather than direct descent in a documented scribal line. The recipient language or community scope is carried in the edge's scope fields. | It does not assert that the recipient language borrowed its vocabulary or grammar from the source script's language. |
| `AREAL_CONVERGENCE` | Undirected or multi-party, among languages in a named area and period, with a named shared feature set. | It does not assert a common ancestor, a single donor, or direct contact between every pair in the set. A multi-party edge is not decomposed into pairwise borrowing edges. |
| `POPULATION_MOVEMENT` | Directed, from a source population or community context entity to a destination population or community context entity, over a stated interval, on a stated archaeological or ancient-DNA basis. | It does not assert language movement, language replacement, or the language spoken by either population. Any language consequence requires a separate sourced assertion and is normally an (H). |
| `PROPOSED_RELATION` | A scholarly-hypothesis edge. The record additionally carries `proposed_predicate`, naming the relationship the scholar or school proposes (for example, a proposed genetic descent or a proposed script relation). Endpoints follow the proposed predicate's rules. | It is not a weaker copy of the proposed predicate and is never traversed, counted, or rendered as if the proposed relationship were established. It records that a proposal exists and who made it. |

`PROPOSED_RELATION` is the graph's scholarly-hypothesis edge. It exists so a contested proposal can be fully represented — proponent, basis, scope, counter-arguments, and removal condition — without contaminating the established-relation layer. Promotion of a `PROPOSED_RELATION` to its proposed predicate is a new reviewed assertion, not an edit of the hypothesis record.

### 2.3 Structural relations, kept apart from history

Three structural relations are required to make the graph usable. They are stored as edges for query convenience but typed as structural, time-scoped, and non-genealogical:

| Relation | Meaning |
|---|---|
| `WRITES` | A script writes a language for a stated period, region, genre, or register. This is the only ordinary bridge between script nodes and language nodes. |
| `ATTESTED_AT` | A language or script is attested at a site or in a named corpus, under a sourced attestation assertion. |
| `ADMINISTERED_BY` / `USED_IN_POLITY` | A language or script is associated with a polity or institution for a stated period and function. This records use, not ownership of the language by the polity. |

A query, export, or visualisation that mixes structural relations with historical predicates must label the layers separately. In particular, a path that runs language → script → script-descent → script → language proves nothing about a relationship between the two languages.

### 2.4 Competing edges and the no-consensus rule

Hypothesis edges from different schools coexist as separate records with their own provenance. The graph does not contain a merge operation that averages them into a consensus edge, a majority edge, or an unlabelled “generally accepted” edge.

The rules are mechanical:

1. Two edges with the same endpoints and predicate but different proponents, bases, scopes, or evidence classes are different assertions and are both retained.
2. Two edges whose predicates or placements conflict are linked by a `CONTESTS` cross-reference between assertions. Neither is deleted or demoted automatically.
3. A catalogue's classification is one sourced assertion among others, with the catalogue's authority recorded as provenance. Authority affects review priority; it does not convert an assertion into an (F).
4. An aggregate view may report “three active placement assertions: one catalogue classification, one school proposal, one program hypothesis.” It may not report a single placement unless the view is explicitly filtered to one named source's assertions and says so in its title and provenance block.
5. Transitive closure is computed only within `GENETIC_DESCENT` and only over edges admitted to the closure by a named release rule. Closure never crosses `PROPOSED_RELATION`, `CONTACT_BORROWING`, `AREAL_CONVERGENCE`, `POPULATION_MOVEMENT`, `SCRIPT_DESCENT`, or `WRITES`.
6. No inference rule may derive a language relationship from a script relationship, a language relationship from a population movement, a population identity from a language label, or a homeland from a findspot centroid. A scholar may assert any of those conclusions as a separate sourced (H) or (K); the graph itself does not derive them.

### 2.5 Edge falsifiers and narrowing

An edge's removal condition must be concrete enough that a future population batch can test whether it has occurred. Acceptable forms include:

- a stated sound correspondence or shared innovation fails on a specified held-out wordlist;
- a sign-form derivation is contradicted by an earlier attested intermediate form;
- a loanword stratum is shown to postdate the claimed contact period;
- a proposed contact zone is shown to have no temporal overlap under a revised chronology;
- an ancient-DNA movement assertion is superseded by a larger or better-dated sample from the same region and period;
- the source corrects, retracts, or replaces the classification on which the edge rests;
- a registered program test returns the verdict the edge's registration named as its falsifier.

An edge may be **narrowed** rather than removed: its temporal, spatial, or feature scope is reduced by a superseding edge. The original remains in earlier releases. A narrowing is often the honest outcome of new work and must be representable without pretending the broader claim never existed.

### 2.6 Worked separations from the three programs

- **Meroitic.** The script's deciphered status sits on the script node. The language's affiliation proposals — Northern East Sudanic in Rilly's position, the Afroasiatic side carried in the program record, and the isolate-for-testing null — are separate placement assertions and `PROPOSED_RELATION` records with their own proponents and removal conditions. No one of them is stored as the language node's family.
- **Eteocypriot.** The `WRITES` relation to the Cypriot syllabary is structural and time-scoped. Proposals linking the language to Hurrian, to a Tyrsenian grouping, or to a Semitic line, all named in the baseline's contact domain as unaccepted proposals, remain hypothesis edges. The bilingual habit attested in the baseline is evidence about use; it is not a genetic edge.
- **Indus.** The program's live family possibilities (Dravidian, Indo-Aryan, Munda or Para-Munda, a lost or isolate family) and the non-linguistic-writing position enter the graph in different places: the family possibilities as hypothesis placements on an inferred or unresolved language record, and the non-linguistic position as a hypothesis about the script node's function. The graph must not force the second into a language-family shape merely to make the diagram tidy.

## 3. Spherical projection and time navigation

### 3.1 What is being specified

This section specifies the owner's directed view: the graph laid on a sphere, using geographic position as the primary spatial organisation, with time as a navigable dimension. It is a specification for a later build. No renderer, globe library, tile service, or interaction library is chosen here, and no view built later may add evidentiary content that this specification does not authorise.

The canonical spatial object is the sphere itself. Two-dimensional outputs are projections of a pinned graph release, generated for a named purpose and reproducible from a saved view state.

### 3.2 Geometry assertions come before coordinates

A renderer never receives a bare latitude and longitude. It receives geometry assertions, each typed, sourced, and scoped:

| Geometry type | Meaning | Rendering treatment |
|---|---|---|
| `ATTESTED_FINDSPOT_SET` | The actual findspots or attestation sites in the record. Stored as a point set or polygon, not pre-collapsed. | Small attested markers or a footprint boundary. |
| `ATTESTED_DISTRIBUTION` | A sourced distribution area for attested use. | A bounded, filled footprint with the source and period in its provenance. |
| `DISPLAY_CENTROID` | A computed representative point for an attested footprint, with the computation method and the footprint it summarises. | A node marker, always linked back to the footprint; the marker is a summary glyph, not a place claim. |
| `INFERRED_HOMELAND` | A proposed homeland or origin area from a named source. Stored as the source's own point or region, with its uncertainty as stated. | Hollow or hatched rendering, visibly distinct from attested geometry in shape and legend, not merely in colour. |
| `RECONSTRUCTED_STAGE_AREA` | An area proposed for a reconstructed or earlier stage of a language, family, or script. | Same inferred treatment as a homeland, plus the reconstruction source in the label. |
| `CONTACT_ZONE` | A sourced area in which a contact, borrowing, or convergence assertion is scoped. | A zone overlay attached to the edge, not a node location. |
| `NO_GEOMETRY` | No defensible geometry exists, or the node's location is the very question at issue. | The node appears in the off-sphere index (§3.6), never at a default coordinate. |

Three separations are mandatory:

1. **Attested findspot centroid and inferred homeland are different assertions.** A node may carry both, either, or neither. They are stored in different fields, rendered in different forms, and exported in different layers. No process may average them into one point.
2. **A centroid is a computation, not a discovery.** Its record names the input footprint, the method, and the release. Moving a corpus boundary recomputes the centroid; the change is a display change, not a historical event, and is logged as such.
3. **An inferred geometry inherits the evidence class of its assertion.** An (H) homeland renders as a hypothesis wherever it appears, including in exported stills. A screenshot may not launder it into a fact by dropping the legend; §3.8's export rule addresses this.

### 3.3 Sphere-first rendering and named 2D projections

The primary view is an interactive sphere: nodes and footprints placed by their geometry assertions, edges drawn as great-circle arcs or footprint-to-footprint connectors, and rotation used to inspect any hemisphere without a privileged centre.

Generated two-dimensional projections are permitted for print, comparison, and accessibility. Each generated view names its projection and its centre or standard parallels in the view state. The design allows, without prescribing implementation:

- an orthographic hemisphere pair for a globe-like static record;
- an azimuthal projection centred on a selected node, site, or contact zone for local inspection;
- a full-sphere rectangular projection for inventory checking only, labelled as area- and shape-distorting.

No projection is the canonical geography. A measurement taken from a 2D view (distance, area, adjacency) is not a graph fact; measurements, where a study needs them, are computed on the sphere from the underlying geometry assertions under a stated method.

### 3.4 Edge rendering across the projection

Edges are rendered by layer, with the layer selected in the view state:

| Layer | Contents | Rendering rule |
|---|---|---|
| Structural | `WRITES`, `ATTESTED_AT`, polity or institution use. | Neutral connectors. An arc means “related records,” never a journey. |
| Genetic | Admitted `GENETIC_DESCENT` edges. | Directed arcs, ancestor to descendant. Only edges admitted by the view's named source filter appear. |
| Contact | `CONTACT_BORROWING` and `AREAL_CONVERGENCE`. | Borrowing is directed and scoped to its period and feature set; convergence is drawn as a zone or multi-party grouping, not as a bundle of pairwise arrows. |
| Script history | `SCRIPT_DESCENT` and `SCRIPT_BORROWING`. | A visually separate layer from genetic descent, with its own legend, so a script lineage can never be mistaken for a language lineage at a glance. |
| Population movement | `POPULATION_MOVEMENT` between population or community context entities. | Rendered only on the population layer, between population entities. The layer may be shown beside the language layers; its arrows never terminate on language nodes. |
| Hypotheses | `PROPOSED_RELATION` edges and (H) placement assertions. | Dashed or otherwise structurally distinct rendering, proponent named on selection. Hypothesis edges are off by default in any view described as showing the established record, and on only under a view title that says hypotheses are shown. |

Additional rendering rules:

- **Parallel edges stay parallel.** Competing assertions between the same nodes are offset or stacked, each selectable, none hidden inside a merged line.
- **Line weight does not encode truth.** Weight may encode a declared display variable such as number of underlying assertions, and the legend must say so. It may not encode confidence, because a thick line reads as a strong fact regardless of the legend.
- **Colour is never the only distinction.** Evidence class and geometry type are distinguished by shape, line pattern, or fill pattern as well as colour, so the epistemic coding survives monochrome printing and colour-vision differences.
- **An arc is not a route.** Unless an edge's own sourced assertion describes a route or movement path, the great-circle connector is a diagrammatic join. Population-movement arrows join source and destination entities; they do not claim the path drawn was travelled.
- **Labels show status.** Selecting or labelling a gap target shows its script or language status code beside the name, so an undeciphered script and a deciphered one are never presented as equivalent objects.

### 3.5 Time as a navigable dimension

Time is a query dimension over intervals, not an animation of presumed spread.

**Time model.** Every attestation, geometry, edge, and covariate assertion carries a temporal scope as an interval with stated uncertainty, stored in a normalised year model that handles BCE and CE without a year zero error. A date known only as a century, reign, stratum, or period label is stored as the interval that label denotes in its own scheme, with the scheme named; it is not sharpened to a midpoint for storage.

**Time slices.** A view state names a time window `[start, end)`. Under a slice:

- a node is shown in its attested form if the window overlaps a sourced attestation or documentation interval;
- a node is shown in its inferred form, with inferred rendering, if the window overlaps only an inferred-existence or reconstructed interval;
- an edge is shown only if its temporal scope overlaps the window and the view's layer and source filters admit it;
- a covariate is shown only within its own scope; a polity that did not yet exist in the window does not appear as a node's polity because it held in another century;
- uncertainty at a boundary is shown as boundary uncertainty (a node near the edge of its interval is marked as such), not resolved silently in or out.

**Navigation.** The build must support stepping by named periods as well as by year windows, because the sources reason in periods. Stepping is a change of query, logged in the view state. An animated transition between slices is a navigation aid; it must not interpolate node positions, grow footprints, or move arrows, because interpolation would manufacture a spread narrative the assertions do not contain. A language or script appears, changes scope, or disappears between slices only as its interval data dictates.

**Coexistence rule.** Two nodes overlapping in a slice are shown as coexisting in the record's terms. Overlap alone generates no contact edge, no shared polity, and no visual grouping beyond coexistence.

### 3.6 Nodes with no defensible position

A node with `NO_GEOMETRY`, and any inferred-unknown node whose only honest geography is a broad trace region, appears in an **off-sphere index** attached to the view: a searchable, first-class list, visibly part of the same release, stating why each entry is unplaced. Placing such a node at 0,0, at a modern capital, at the centroid of a modern country, or at a scholar's guessed point without an `INFERRED_HOMELAND` assertion is prohibited. The size of the off-sphere index is itself reported in the view provenance; a globe that quietly omits its unplaced nodes misrepresents the record.

### 3.7 View state and reproducibility

Every saved or exported view carries a view state:

- graph release ID and snapshot hash;
- schema version;
- projection and centre, or sphere orientation;
- time window and period scheme;
- layers on or off;
- source filter, if any (for example, “Glottolog classification assertions only”);
- evidence-class filter, if any;
- geometry types admitted;
- the count of nodes in the release, the count rendered, and the count in the off-sphere index.

Rebuilding the view from its state and release must reproduce it. A view that cannot be so reproduced is a sketch, and is labelled as one wherever it is filed.

### 3.8 What the projection must never imply

The following are acceptance rules for any later build, not stylistic advice:

1. **Visual proximity is not evidence.** Two nodes near one another on the sphere are near in geography only, under the geometry assertions stored. Proximity generates no relationship, and no layout algorithm may reposition nodes for legibility in a way that changes their geographic meaning. Where labels collide, labels move; nodes do not.
2. **An attested centroid is not a homeland.** The legend and the node's provenance panel must keep the geometry types named in the user's own language.
3. **An inferred position is not an attested position.** The distinction must survive zooming, exporting, screenshotting, and monochrome printing. Every export carries its legend and provenance block embedded in the image or document, not in a separate file that can be detached.
4. **An arc is not a route, a migration, or a direction of influence** beyond what the underlying edge asserts.
5. **Empty space is not absence.** Oceans, deserts, and unexcavated or unpopulated regions of the map show only that the release carries no geometry there.
6. **Modern borders are not ancient geography.** A modern-boundary overlay, if offered at all, is off by default, labelled modern, and never used as a node's polity or region value.
7. **Time overlap is not contact.** The slice mechanism shows coexistence; contact requires its own edge.
8. **A family tree laid on a map is not a migration history.** Genetic-descent arcs show claimed descent, not the path or movement of speakers.

## 4. Gap register

### 4.1 Purpose

The gap register is the graph's working conscience. Every undeciphered script and every not-understood language in a release has exactly one gap entry. The register converts “we do not know” from a narrative aside into a structured, auditable object: what is known, what is missing, which placements have been proposed, what would move the case, and how strongly the program prioritises it.

A gap entry is not a research conclusion. It is a standing description of an epistemic state, versioned with the graph.

### 4.2 Generation rule

A gap entry is generated automatically, and may not be waived, for:

- every script node whose current decipherment assessment is `S0`, `S1`, or `S2`;
- every language node whose current understanding assessment is `L0`, `L1`, or `L2`;
- every language node whose status is `L3` but whose family placement is `PLACEMENT_UNRESOLVED` (a classification gap attached to an understood language);
- every inferred-unknown node, whatever its other fields;
- every script node whose linguistic status is itself in dispute, including a node that may not encode language at all.

A node at `S3`/`S4` and `L4`/`L5` with a resolved placement has no gap entry unless a reviewer opens one for a named residual question. Gap entries are closed, never deleted, when their movement conditions are met (§4.5).

### 4.3 Gap-entry schema

| Field | Requirement |
|---|---|
| `gap_id` | Persistent opaque ID. |
| `target_node_id` | Exactly one language or script node. Where a script and its language are both gaps, they have separate entries cross-linked to each other. |
| `gap_kind` | `SCRIPT_UNDECIPHERED`, `LANGUAGE_NOT_UNDERSTOOD`, `SCRIPT_AND_LANGUAGE`, `CLASSIFICATION_UNRESOLVED`, `ATTESTATION_ONLY`, or `LINGUISTIC_STATUS_DISPUTED`. |
| `current_status` | The target's current status assessment and the release in which it was made. |
| `known` | A list of assertion IDs: the positive knowledge that bounds the gap (attestation, corpus, deciphered subsystems, understood formulae, anchors). Each item is sourced through its assertion. |
| `missing` | A list of named missing elements, each typed: `SIGN_VALUES`, `SEGMENTATION`, `LEXICON`, `GRAMMAR`, `BILINGUAL_OR_PARALLEL`, `RELATED_LANGUAGE_IDENTIFICATION`, `CORPUS_SIZE`, `CORPUS_ACCESS`, `SOURCE_ACQUISITION`, `EXPERT_VERIFICATION`, `GENRE_BREADTH`, or another controlled type. A missing element names what is absent, not merely that knowledge is incomplete. |
| `blockers` | Each blocker typed as `INFORMATION` (the evidence does not exist in the held record), `ACCESS` (it exists but is not held or not permitted), `POWER` (a test exists but cannot decide at the available N), `PERMISSION` (a gate or licence controls use), or `EXPERTISE` (a named verification has not been returned). |
| `candidate_placements` | An ordered list of references to placement assertions and `PROPOSED_RELATION` edges, each with its evidence band (§4.4), its supporting and opposing assertions, and its removal condition. |
| `movement_conditions` | The observations, acquisitions, or registered tests that would change the status, narrow the gap, promote or withdraw a candidate, or close the entry as indeterminate. Each condition names the status or candidate it affects. |
| `priority` | The priority object of §4.6. |
| `linked_tests` | Registered program tests or gates that bear on the gap, with their current state. A link does not commission, amend, or reopen any test. |
| `custody_and_access` | Any custody terms, licences, or permission gates that constrain work on the target's evidence, stated at the register's face. |
| `last_reviewed` | Release and date of the last review, and the reviewer. |

### 4.4 Ranking candidates by evidence, honestly

Candidates are ranked by **evidence band**, not by a fabricated probability:

| Band | Meaning |
|---|---|
| `A` | The candidate is supported by a passed, registered, adequately controlled test or by decipherment-grade convergent evidence, and survives in the current record. |
| `B` | The candidate has positive filed support from a controlled analysis that did not meet its decision bar, or from one passed supporting leg beside a failed or unrun principal leg. |
| `C` | The candidate is a named scholarly or program proposal with a stated basis and a falsifier, but no program-tested support. |
| `D` | The candidate is named in the literature or record without a basis the population process could open and check. It is retained for completeness and labelled accordingly. |

Within a band, candidates may be ordered for work by testability — specificity of falsifier, availability of comparanda, and cost of the discriminating test — and the register must say that the within-band order is a work order, not a likelihood order. Ties are shown as ties. A candidate's band changes only by a reviewed assertion citing the test or source that moved it.

The null is not a candidate. “Isolate,” “unrelated to the tested families,” and “not linguistic writing” are status outcomes or hypotheses about the target's nature, recorded in the hypothesis set; they are not placements and are never ranked as if they were families.

### 4.5 Gap lifecycle

A gap entry carries one lifecycle state:

- `OPEN` — described, no discriminating work in progress;
- `TESTABLE` — at least one registered or registerable test with complete inputs exists;
- `BLOCKED_EXTERNAL` — every discriminating route waits on a named external input;
- `IN_PROGRESS` — a commissioned test or acquisition bearing on the entry is running;
- `NARROWED` — at least one candidate has been withdrawn or a status boundary has moved, with the gap still open;
- `RESOLVED` — the target has crossed the status threshold that generated the entry, on evidence admitted through the owning program's own gates;
- `CLOSED_INDETERMINATE` — the available evidence has been shown, by a filed power or identifiability result, insufficient to decide the entry's question at present. This is a substantive closing state, not a failure label, and it reopens only on a named change in evidence, access, or method.

Movement between states is a ledgered event citing the assertion, test, or acquisition that caused it.

### 4.6 Priority

Priority is a structured object, not a single unexplained number:

| Dimension | Values and meaning |
|---|---|
| `owner_priority` | `1` for the three Glossa-Lab programs, by the owner's direction; `2` for gaps directly bearing on a Priority-1 gap (a candidate relative, a contact language, a script ancestor); `3` for the remaining census. Owner priority expresses where the program's attention goes; it is not a claim about importance to the field. |
| `readiness` | `READY` (inputs held, test registerable), `PARTIAL` (some inputs held, named items outstanding), or `BLOCKED` (a named external input controls every route). |
| `expected_learning` | The active decipherment loop's current assessment, by reference to its ranking record where one exists. The graph does not compute its own rival ranking. |
| `blocker_class` | The dominant blocker type from §4.3, so the owner can see at a glance whether the portfolio is short of information, access, power, permission, or returned expertise. |

The register's default work queue sorts by owner priority, then readiness, then the loop's expected-learning order. A sort order is a work queue, never a probability that a gap will close.

### 4.7 Worked example — Indus

**Targets.** Two cross-linked entries: the Indus script node (`SIGN_LIST_UNIT` or `ATTESTED`, as the population review settles the corpus-convention question) and an inferred-unknown language record for whatever the script encodes, if it encodes language.

**Current status.** Script: structural derivation exists (the Spec 105 ladder and its positional and substitution results), but no sign values are established; the assessment sits at the S0/S1 boundary and the population review must fix it against the §1.7 definitions with its basis stated — this design does not pre-judge that call. Language: `L0` as an inferred record, with the non-linguistic-writing hypothesis carried openly as a dispute about the script's function (`LINGUISTIC_STATUS_DISPUTED`).

**Known (from the filed record).** A working corpus of 1,670 artifacts; a sandbox derivation set of 1,336 artifacts and 5,611 tokens with 372 marks (390 in the full corpus); positional structure including exactly one mark, M220, that is only group-final in 53 of 53 occurrences; an anchor register of 287 anchors with a 94 strict core standing 3 established, 66 inferred, 4 refuted, 3 probable, 18 unresolved; a baseline world model of 88 axioms for the mature Harappan frame, c. 2600–1900 BCE.

**Missing.** Secure sign values; secure segmentation into words; a bilingual or externally anchored parallel; a securely identified related language; independent sourcing for the anchor register — exactly 1 of the 94 strict-core anchors (M047) is independently sourced, which the program record names as the binding weakness.

**Blockers.** Dominant: `INFORMATION`. Also `PERMISSION` on one route: the Holdat corpus's per-seal iconography exists only in custody, its terms allow published statistics but no redistribution, and the registered route to the motif join is Spec 100, whose gate opens only on the corpus holder's reply, which has not arrived.

**Candidate placements.** All are hypothesis edges; none is a node fact. In evidence-band terms, no candidate carries program-verified placement support. The Dravidian line carries the largest body of filed, falsifiable program material (the anchor register itself) and is therefore first in the work queue on testability, with the register's own caveat displayed beside it: investigation volume is not support, and independent sourcing stands at 1 of 94. The Indo-Aryan, Munda or Para-Munda, and lost-or-isolate possibilities stand in Band C as named members of the program's hypothesis set. The Meluhha material is recorded, per the active decipherment design, as prior-odds context for the affiliation hypotheses, never as likelihood evidence about sign values.

**Movement conditions.** A second independent blind coding return; the Spec 100 gate opening; an external corpus match that independently sources further anchors; the commissioned identifiability calibration (test I-1 in the active design) returning a recovery result that licenses or closes the structural queue; a normalised replay settling the G-IND predictive question (test I-4). Any one of these narrows the entry; none is represented as a decipherment.

**Priority.** `owner_priority 1`; readiness `PARTIAL`; dominant blocker `INFORMATION`.

### 4.8 Worked example — Eteocypriot

**Target.** The Eteocypriot language node (`ATTESTED`). Its script relation is to the Cypriot syllabary, whose sign values the program record treats as settled; the syllabary node therefore carries no script gap of its own, and the entry is a language gap only. Keeping those facts apart is the example's point.

**Current status.** Language `L1`: attested, transliterable, not understood, with externally anchored personal names in the bilingual material but no reliable lexicon or grammar.

**Known.** The Amathus bilingual (ICS 196) with its Greek parallel and the dedicator and honorand named in the program's ensemble record (the city of the Amathusians; Ariston, son of Aristonax); a sandbox development corpus of 2 artifacts, 3 lines, 14 groups, 69 tokens, and 35 derived marks, 18 of them singletons; the Perna 2019 census of ICS 194/195 readable in full at 216 signs; the Eteocypriot baseline of 71 axioms for Iron Age Cyprus.

**Missing.** Corpus, above all: the pilot's registered prediction floor of 100 legible signs of unseen held-out continuous text was met by zero held signs at freeze. Also missing: the edition-of-record portion copy for ICS 196 (requested through interlibrary loan on 2026-11-22, unanswered), a returned second-reader verification (Steele, commissioned 2026-11-23, no reply on the record), and a returned completeness check (Egetmeyer, invited 2026-11-23, no reply on the record).

**Blockers.** Dominant: `INFORMATION` (corpus size in existence, not merely in hand). Secondary: `ACCESS` and `EXPERTISE` on the named outstanding inputs.

**Candidate placements.** The baseline's contact domain names Hurrian, Tyrsenian or Etruscan/Lemnian lines, an Anatolian affiliation for the wider grouping, and a Northwest Semitic conjecture, each as unaccepted proposals. All stand in Band C: named, sourced to their proponents as filed, falsifiable in principle, with no program-tested support and no likelihood order among them. The pre-Greek isolate position is the unresolved-placement state, not a ranked candidate.

**Movement conditions.** Execution of the already-registered Spec 101 postdictive enrichment test on a fresh owner commission (its target standing as declared: enrichment, expressly not a recurrence finding); arrival of the ICS 196 portion copy; either expert reply; the control-corpus calibration (test E-2) settling which statistics may be argued from at this corpus size. The entry's honest resting state, if none of these moves it, is `CLOSED_INDETERMINATE` at the corpus floor — a state the program has already returned once for the prediction leg and must be willing to return again.

**Priority.** `owner_priority 1`; readiness `PARTIAL` (one fully registered test awaits only a commission); dominant blocker `INFORMATION`.

### 4.9 Worked example — Meroitic

**Targets.** Two entries that must never be merged: the language node (`ATTESTED`) with a classification and understanding gap, and no script gap — the Meroitic script node is deciphered.

**Current status.** Script `S3`: sign values established by Griffith's decipherment, the standard against which the program's G-MER gate checks derived structure. Language `L2`: a bounded vocabulary and formula system understood (the baseline records c. 100 securely translated words at its cited resolution; the program's candidate tests returned 1 partially supported and 5 unsupported among six candidates), while ordinary continuous text and affiliation remain unresolved.

**Known.** A corpus of record (the Kovetsky build: 396 inscriptions, 368 distinct texts) with a filed genre stratum for every text; sandbox streams of 5,195 groups and 29,843 tokens over 32 marks; conformance results for the a-sign and i-sign restrictions at 725/737 (98.4%) and 2,857/2,880 (99.2%) against the registered tolerance; a completed source-witness check (Spec 103) under which five candidate forms' claims stand and one, asoreyi, is not checked because the held edition of record prints no transliteration for the two texts that would decide it.

**Missing.** An adequately powered affiliation test. The Stage 4.2 result stands UNDECIDABLE AT THIS POWER (R1 vocabulary S = 4/12 at permutation p = 0.0326 against a bar of p < 0.01 and S ≥ 5; the R1 formative leg passed as supporting only; R2 vocabulary S = 1/12). The held-material ceiling is proven: 182 frozen forms yield exactly 12 ASJP concepts, against Spec 102's gates of at least 40 scored concepts per family test with at least 20 outside the earlier twelve (G-1) and at least 80% injection power at the registered parameters (G-2).

**Blockers.** Dominant: `POWER`, with an `ACCESS` component now largely discharged — the Rilly & de Voogt 2012 Appendix lexicon is in custody under its registered terms, and Rilly 2010 is in transit with no delivery estimate given. The remaining gate is the owner's commission, which is a decision, not a blocker the register may route around.

**Candidate placements.** Ranked by evidence band on the filed internal record: the Northern East Sudanic line (Rilly) stands in Band B — its formative leg passed its bar as supporting evidence while its vocabulary leg fell short of the joint decision bar — and the Afroasiatic line stands in Band C on the program's internal record, its filed vocabulary result at S = 1/12 and its phonotactic leg not passed at Stage 4.2, with Rowan's published phonotactic argument recorded as its scholarly basis for re-derivation in the proposed battery (test M-2), not as a program result. The isolate-for-testing position is the null of the design, not a candidate. Neither band is a probability, and the standing verdict remains UNDECIDABLE AT THIS POWER until Spec 102 runs at its gates or closes as NOT ADMINISTERED.

**Movement conditions.** Book 1's delivery and digitisation under the registered terms, completing Spec 102's source requirement; the G-1 coverage computation on the actual expanded lists; the G-2 injection simulation on those lists; the owner's commission; the stratum-conditioned recomputation (test M-1) and the stratified phonotactic battery (test M-2) as internal evidence that raises or removes supporting legs without touching the affiliation verdict, which remains Spec 102's alone.

**Priority.** `owner_priority 1`; readiness `PARTIAL` moving to `READY` on book 1's arrival plus commission; dominant blocker `POWER`.

### 4.10 The rest of the census

Every other undeciphered script and not-understood language enters by the same generation rule, with the same fields. Entries outside the three programs will initially be thinner; the register records their coverage depth honestly (§6.5) rather than padding them to the worked examples' depth. A thin entry is a true record; a padded one is a false one.

## 5. Epistemic management

### 5.1 The graph is evidence infrastructure, not a fourth baseline

The graph does not join the three baselines as a peer and does not outrank them. It is a sourced evidence and context system from which baseline amendments may draw. The direction of authority is fixed:

```text
primary sources and catalogues
        │  extraction + verification (§6)
        ▼
graph release  ──►  axiom candidate pack  ──►  human/program review
                                                      │ adopted items only
                                                      ▼
                                            baseline amendment (new
                                            template version, new pin)
                                                      │
                                                      ▼
                                            future instance seeds
```

Nothing flows the other way automatically. A program result (a verdict, a standing, a gate outcome) may be recorded in the graph as a program-record assertion with its provenance, but recording it does not change its status, and a graph process may never restate a program result in stronger language than the program's own record uses.

### 5.2 Which graph content may become an axiom, and of which class

A graph assertion becomes a baseline axiom only by adoption in a baseline amendment. The class it may carry is determined by what it is, not by how authoritative its source feels:

| Graph content | Highest class on adoption | Reason |
|---|---|---|
| A directly checkable record fact: a named inscription exists in a named corpus; a text is held in a named custody home; a book was delivered on a stated date. | (F), if doubting it means doubting the program's own record itself. | This is the framework's floor test, applied as written. Most graph content will not meet it. |
| A well-supported scholarly position with a named source: a catalogue classification, a decipherment history, a dated attestation, a corpus count under a stated convention, an ancient-DNA result at its published resolution. | (K). | Period knowledge is revisable by definition. A catalogue's classification is (K) at best, however standard the catalogue is. |
| A contested placement, a proposed homeland, a reconstructed stage, a population-to-language consequence, a substrate inference, any UNSOURCED variable. | (H). | Declared openly or not adopted. |
| A rendering product: a centroid, a map cluster, an arc, a time-slice coexistence. | Never an axiom. | Views are not evidence (§3.8). |
| A gap-register state or priority value. | Never an axiom. | Register states describe our knowledge and our attention; they are not premises about the past world. |

Two further rules:

- **Class is set at adoption, on the adopting record.** The graph stores evidence class as its own assessment; the baseline amendment re-tests the line against the framework definitions and may adopt it at a lower class. It may never adopt it at a higher class than the graph's assessment without a new source named in the amendment.
- **One axiom, one graph assertion (or an explicitly listed set).** A baseline line that synthesises several graph assertions lists all of them in the baseline-links mapping. Synthesis hidden inside a single citation is the graph-era form of smuggling and is prohibited.

### 5.3 Propagation: from graph update to baseline pin

A graph update never edits a baseline. Propagation is a five-step, fully ledgered pipeline:

1. **Graph release.** A verified batch lands as a new immutable graph release with its own snapshot hash (§5.4). The release note lists added, superseded, narrowed, and withdrawn assertions.
2. **Impact report.** A generated diff is classified per affected baseline: `ADDITIVE` (new context, no existing axiom touched), `CORRECTIVE` (an adopted assertion was superseded or narrowed), `CONTRADICTORY` (a new reviewed assertion conflicts with an adopted axiom's statement), or `EDGE_ONLY` (relationships changed; no adopted field assertion affected). The report names the axiom IDs at stake through the baseline-links mapping.
3. **Program review.** A reviewer decides, per affected axiom, to adopt, defer, or decline the change, with reasons. Silence is not adoption; an unreviewed impact report changes nothing.
4. **Baseline amendment.** Adopted changes land as a new template version under the framework's existing amendment discipline: the old version's seed record stands, the new version carries its own census and pin, and the amendment is logged in the study's seed-and-iteration log with the graph release ID as its source. The Meroitic template's version 2 amendment of 2026-11-25 is the existing precedent for this shape.
5. **Forward-only effect.** Instances already seeded keep the template version they were seeded from. Completed ensembles are not re-read under the new version. If a correction touches an axiom that was load-bearing in a completed ensemble, the impact report says so, an addendum is appended to that ensemble's outcome record, and whether to re-run is a fresh decision at the reasoning level — never an automatic re-run and never a silent reinterpretation. The Round N conformance annotations on the Spec 105 Stage 6 outcome record are the program's existing precedent for qualifying a filed result without rewriting it.

If a graph assertion adopted into a baseline is later withdrawn at source, the pipeline runs again in the corrective direction. The baseline history will therefore show the line's whole life: adoption, supersession, and the releases in between.

### 5.4 Pins and snapshot identity

Three hashes are kept distinct and never substituted for one another:

- **Graph snapshot hash:** SHA-256 over the canonical serialisation of the release's node, edge, assertion, and gap streams, in ID order, under the schema version. It identifies the graph content.
- **Source-manifest hash:** SHA-256 over the release's source records. It identifies the evidence base the content was extracted from.
- **Baseline axiom-line pins:** the existing per-template SHA-256 values over axiom lines as filed. A graph release does not recompute or replace them; a baseline amendment produces a new template pin in the template's own record.

A citation of graph content is complete only when it names the graph release ID and the assertion or edge ID. “The graph says” is not a citation.

### 5.5 Audit checks, analogous to TC-106-02/03/05

The graph carries its own acceptance checks, modelled on Spec 106's census audits. A release that fails any check does not ship; the failure is a ledger entry, not a warning.

| Check | Analogue | Pass condition |
|---|---|---|
| `WLG-01` Package and schema form | TC-106-01 | Every stream parses; every record carries its kind's required fields; all IDs resolve; no duplicate IDs. |
| `WLG-02` Label and source audit | TC-106-02 | Every field assertion and edge carries exactly one evidence class and either a named, opened source or the UNSOURCED flag; every UNSOURCED item is class (H); no (F) item is unsourced; every (H) item carries a removal condition. |
| `WLG-03` Shared schema conformance | TC-106-03 | Language and script kinds are never conflated; permitted endpoint kinds hold for every predicate; status values come from the §1.7 scales; structural and historical layers are disjoint in storage. |
| `WLG-04` Completeness and gap coverage | New, from §4.2 | Every node meeting a gap-generation threshold has exactly one gap entry; every gap entry's known and missing lists are populated; every candidate in a gap entry resolves to a live placement assertion or hypothesis edge. |
| `WLG-05` Census and pin verification | TC-106-05 | The release's stated counts (by node kind, subtype, status, evidence class, gap kind, and predicate) recompute exactly from the streams, and the snapshot and source-manifest hashes recompute exactly. |
| `WLG-06` No-standing-moves audit | TC-106-06 | The release diff contains no edit to any program record of a standing, verdict, or tally; no hypothesis edge has been traversed in any generated closure; no node field has been populated from a neighbouring node, a population edge, or a rendering product. |
| `WLG-07` Geometry audit | New, from §3 | Every rendered coordinate resolves to a typed geometry assertion; attested and inferred geometries are in separate layers; no node sits at a default or fallback coordinate; every exported view state reproduces its view. |
| `WLG-08` Temporal audit | New, from §3.5 | Every interval is well-formed in the normalised year model; no edge is rendered in a slice its temporal scope does not overlap; period labels resolve to their named schemes. |
| `WLG-09` Competition preservation | New, from §2.4 | Where a release's sources contain competing placements or relations, the competing assertions are all present as separate records; no merge, majority, or consensus record exists that its sources do not themselves state. |

The audits are mechanical where the underlying discipline is mechanical, following the Spec 106 precedent: the census audits caught real defects in the existing baselines (the Round N seed-record count errata), which is the standing evidence that this layer earns its keep.

### 5.6 History-ledger standard applied to the graph

The graph keeps a history ledger in its own package, under framework §10, opened with its commission entry when the build is commissioned. Entries carry date, kind (COMMISSION, DECISION, ITERATION, FAILURE, CORRECTION, VERDICT, GAP, CLOSING), actor or authorising act, what happened and why, and checkable references.

In addition to the standard kinds, the graph ledger records, per population batch: the batch manifest (§6.4), the audit outputs, the quarantine list, and the release the batch produced. Per correction: the superseded assertion, its replacement, and the impact reports sent to the baselines. Per identity event: any node merge, split, or re-subtyping, with its identity criteria cited.

The separation rule applies with its usual force: papers and reports cite the graph ledger and the graph release; they do not narrate the graph's construction history from memory, and the ledger does not argue for results.

### 5.7 The placement rule, stated once and enforced everywhere

**A placement estimate is a hypothesis edge or a placement assertion, never a node fact.**

Enforcement is architectural, not editorial:

- the node schema has no unqualified family field to fill;
- exports that list a “family” column must generate it from a named source filter and label the column with that source;
- the spherical view's default layer shows placement assertions only when a source filter is named in the view title;
- the active decipherment loop may read candidate placements from the graph as its hypothesis queue input, but each candidate enters a registration with its own falsifier and nulls, exactly as the active design already requires — the graph supplies the queue, never the verdict;
- a placement's promotion path is: hypothesis edge → controlled test or convergent decipherment-grade evidence → reviewed placement assertion at a higher band → possible baseline adoption as an (H) or, where the framework test is met, a (K). There is no shorter path, and no path that runs through the map.

### 5.8 How the loop consumes the graph

The active decipherment loop and the graph have a narrow, declared interface:

- **Inputs from the graph to the loop:** gap-register work queues; candidate placement assertions with their evidence bands and removal conditions; covariate assertions (genre, site, period, polity) for test design; and the source registry's record of what is held, what is in transit, and what is access-blocked.
- **Outputs from the loop to the graph:** outcome records, filed as program-record assertions with their spec provenance; band changes for candidates a test has moved; gap lifecycle transitions with the test cited.
- **What never crosses:** a loop ranking does not become a graph confidence label; a graph confidence label does not become a loop likelihood. Each system keeps its own assessments under its own name, so a reader can always tell which discipline produced a number or a label.

Both systems pin each other by release and record ID at the moment of use. A loop cycle that consumed graph release 7 says so in its ranking record; a graph release that records a loop outcome names the spec record it came from.

## 6. Population plan

### 6.1 Principle: census first, depth where it bears

The population goal is a complete census at honest depth: every language and script in scope present as a node, every undeciphered or not-understood case present as a gap, and deep, fully verified dossiers where the graph bears on the program's work — around the three priority gaps, their candidate relatives, their contact zones, and their script lineages. Completeness of coverage and completeness of depth are different claims, and every release states both: how many nodes it carries, and at what coverage depth (§6.5) each stands.

No batch may silently narrow the census. An item a batch cannot process is quarantined with a reason and carried in the batch report; the census count is the count attempted, the count landed, and the count quarantined, all three.

### 6.2 Batch sequence

| Batch | Scope | Primary products |
|---|---|---|
| `B0` Authorities and crosswalks | Pin the classification and catalogue versions in force; build identifier crosswalks between the graph's persistent IDs and external catalogue IDs; settle name and alias handling. | Source-registry foundation; crosswalk records; the pinned-version policy of §6.6. |
| `B1` Global skeleton | Language and script nodes at skeleton depth for the full census, from the pinned classification source and script references. Statuses assigned conservatively; anything not verified at this pass is `NOT_ENUMERATED` or `UNKNOWN`, never guessed. | Node census; first gap generation from status thresholds. |
| `B2` Decipherment histories | For every script that has been deciphered, partly deciphered, or claimed deciphered: the primary decipherment record, its independent verification, and the current status assessment with its basis. Claimed decipherments that the scholarly record does not sustain are recorded as claims with their standing, not as decipherments. | Status assertions for script nodes; decipherment-history assertions; a claims record that keeps failed decipherments visible as history. |
| `B3` Family, contact, and script-history edges | Genetic, contact, areal, script-descent, and script-borrowing assertions, family by family, with competing school proposals entered as separate hypothesis edges. | The historical edge layers, with competition preserved. |
| `B4` Movement and covariates | Population-movement assertions from the ancient-DNA and archaeological literature; culture, period, geography, religion, and polity covariate blocks for the nodes they concern. | Population layer; covariate blocks; contact-zone geometries. |
| `B5` Gap census completion | Every gap entry reviewed against §4.3: known, missing, blockers, candidates with bands, movement conditions, priority. | The complete gap register. |
| `B6` Priority reconciliation | The three programs' nodes, edges, and gaps reconciled line by line against the filed program record (Specs 096–106 and the baselines), which governs wherever the general literature and the program record differ in scope. | The three worked dossiers at full depth; baseline-links mappings for every adopted assertion. |

Batches B2–B4 may run in parallel by region or family once B1's identities are stable. B6 runs last for the priority dossiers because it depends on the general layers existing to be reconciled against.

### 6.3 Source hierarchy, by role

There is no single hierarchy for all questions; authority is role-specific. A source outranks another only for the questions its kind of evidence answers.

| Question | Governing source kind | Notes |
|---|---|---|
| Language inventory and classification skeleton | **Glottolog**, at a pinned version, for classification and inventory. | Glottolog is the classification authority of record for the skeleton. Its classification enters as a sourced (K) assertion with Glottolog as proponent, not as an (F) and not as the only assertion where scholarship competes. |
| Decipherment status and history | The primary decipherment literature and corpus editions; independent replication or subsequent specialist use as the verification record. | A decipherment's status rests on whether the field can use it, evidenced in the literature, not on the original claim alone. Histories and encyclopaedias are finding aids and synthesis, cited as such. |
| Attestation, corpus, and text facts | Corpus editions, excavation and museum records, and the program's own filed records for its three corpora. | Counting conventions are stored with the count. Where editions disagree, both counts stand with their conventions. |
| Genetic and contact relationships | The comparative literature for the family in question: handbooks, family studies, and the primary proposals and critiques. | Majority and minority positions are both entered, with proponents. A handbook's silence is not a negative assertion. |
| Population movement | Primary ancient-DNA papers and their data supplements for the genetic claim; archaeological literature for context and interpretation. | A genetics paper sources a movement or admixture assertion about its sampled population. It does not source a language label, a language movement, or an ethnic identity; any such further claim needs its own source and is normally (H). |
| Geography, polity, religion, culture covariates | Regional archaeological and historical literature, site reports, and reference works for the region and period. | Covariates are scoped to their evidence (§1.8); a regional synthesis does not license site-level precision. |
| Program-internal facts | The Glossa-Lab filed record: specs, records, ledgers, and custody documents. | For the three programs, the filed record governs scope and status wherever a general source speaks more loosely. |

Tertiary and general-reference material (encyclopaedia summaries, news, unsourced web text) may be used as a discovery lead. It may not be the sole support for an (F) or (K) assertion in a release. Where a baseline already cites such a source at search-result depth, the graph records that depth honestly rather than upgrading it.

### 6.4 Per-item confidence and evidence mapping

Each extracted item carries three independent labels, set by different judgments and never collapsed into one score:

1. **Evidence class (F/K/H)** — the ELSEWHERE class, assigned by the framework test: floor fact, sourced period knowledge, or declared hypothesis.
2. **Source grade** — `P1` primary data or primary literature; `P2` peer-reviewed synthesis or scholarly handbook; `P3` scholarly reference work; `P4` tertiary or general reference. Source grade describes the source, not the claim's truth.
3. **Review state** — the §1.4 ladder, from `UNREVIEWED` to `ADJUDICATED`.

Mapping rules:

- An item may not carry (F) unless it meets the framework floor test on its own content, whatever its source grade. A P1 source does not make a contested classification a floor fact.
- A classification or placement from any single authority enters at (K) at best, as that authority's assertion.
- A proposal, reconstruction, homeland, or population-to-language inference enters at (H) unless the population review records the specific convergent evidence that supports adoption as (K) in a baseline amendment — and even then it enters the graph as a reviewed assertion with its basis listed, so the reasoning is inspectable.
- Confidence labels (§1.4) are assigned at review, with the reviewer's basis stated in one line. `SECURE` is reserved for items whose removal condition is a record correction rather than a scholarly reversal (for example, “this inscription is held in this corpus”), and is never used for a placement.

### 6.5 Coverage depth

Every node carries a `coverage_depth` state per release:

| Depth | Meaning |
|---|---|
| `SKELETON` | Identity, kind, subtype, status, and catalogue cross-reference verified; covariates and edges largely unpopulated. |
| `STANDARD` | Attestation, region, corpus class, placement assertions, and principal edges populated and source-checked. |
| `DOSSIER` | Full covariate blocks, competing assertions adjudicated for the record, gap entry at §4.3 completeness, and independent verification of high-impact edges. |

The three priority programs are populated to `DOSSIER`. Their candidate relatives, contact languages, and script ancestors are populated to at least `STANDARD`, and to `DOSSIER` where a registered test depends on them. The remainder of the census is populated to `SKELETON` in B1 and raised batch by batch, with the release note stating the counts at each depth. Depth is a property of our work, not of the language, and is labelled as such wherever it is displayed.

### 6.6 Version pinning and refresh

External authorities drift. The graph pins the version of each authority it uses (beginning with the Glottolog version adopted in B0) in the source record, and a release names the versions it was built against. Refreshing an authority is a population batch in its own right: extract the differences, enter supersessions, run the impact pipeline of §5.3 for any baseline that adopted the changed assertions, and ledger the refresh. The graph never silently re-points at a newer authority version.

### 6.7 The verification pass

Every batch passes the same gate before any of its items enter a release:

1. **Extraction with locators.** The extractor records each item with its source locator and scope. An item without a locator does not proceed.
2. **Source check.** A verifier other than the extractor (a second worker, a second pass under a different brief, or the program reviewer) opens the source at the locator and confirms the item says what the source says, at the scope the source claims. Mismatches return to extraction; they are not fixed by the verifier's memory.
3. **Type discipline check.** The verifier confirms the language/script/population separations, the predicate choice, and the geometry typing for the batch's items.
4. **Competition sweep.** For each placement or historical edge in the batch, the verifier searches the batch's own source set for a competing position. A found competitor is entered, not adjudicated away.
5. **Independent duplicate extraction for high-impact items.** Items that would change a priority gap's candidate band, a baseline-adopted assertion, or a status assessment are extracted twice, independently, and reconciled. Disagreement quarantines the item for adjudication.
6. **Mechanical audits.** WLG-01 through WLG-09 (§5.5) run over the candidate release. Failures block the release.
7. **Batch report and ledger entry.** The batch closes with a report — attempted, landed, quarantined, and the reasons — filed and ledgered, whether or not the batch fully succeeded. A partial batch reported plainly is a good record; a partial batch reported as complete is a defect.

Progress reporting follows the program's standing constraint: each batch emits timestamped progress indicators (items verified of items attempted, with the current family or region named), so a slow batch is distinguishable from a stuck one.

### 6.8 Access, licensing, and custody

Population work respects the access terms of everything it touches. Sources under licence or custody terms (including the program's own held corpora: the Holdat corpus, whose statistics are publishable but whose scans and rows are never redistributed; the Otten build, held under its no-licence custody terms with aggregate-only derivation; and the Rilly & de Voogt Appendix, held for scoring and aggregate use without redistribution of the lexicon text) contribute only what their terms permit. The graph records the terms on the source record and on any assertion derived from the source, so a later export can be checked against them mechanically. Restricted content is never committed to the graph package; the graph stores the assertion and the pointer, not the restricted bytes.

## 7. Build interfaces and acceptance gates (summary)

A later build commission should be scoped against these interfaces, which this design fixes:

- **Read interface.** Any consumer (the spherical view, the loop, a baseline amendment, a report) reads a named graph release by ID and receives content with its assertion-level provenance intact. There is no “latest, unprovenanced” read mode.
- **Write interface.** Writes arrive only as population batches under §6.7. There is no direct record editing; a correction is a supersession produced by a batch or a correction record.
- **Export interface.** Exports are generated from a release and carry the release ID, the source filters applied, and the epistemic legend. An export that strips provenance is out of specification.
- **Loop interface.** As §5.8: queues and covariates out, outcome records in, each side pinned by ID.
- **Acceptance gates for the build itself.** The build is accepted only when: the WLG audits run and pass on a test release; a view reproduces from its view state; the off-sphere index is demonstrably complete for its release; a competing-placement case (Meroitic) renders as competing assertions under every default view; and a no-standing-moves audit over the build's own test landings is clean.

## 8. Decisions for the owner

This design executes nothing. To commission the build and population, the owner would need to decide:

1. **Adopt the ontology**: languages and scripts as distinct node kinds; proto-language and inferred-unknown subtypes with their restrictions; gap entries as epistemic overlays; population movement confined to population entities.
2. **Adopt the two status scales** (script S0–S4, language L0–L5) and the rule that a script's status never transfers to its language.
3. **Adopt the edge discipline**: the seven historical predicates with `PROPOSED_RELATION` as the scholarly-hypothesis form; competing edges preserved; no consensus merging; no cross-type inference.
4. **Adopt the spherical view specification**, including typed geometries, the attested/inferred rendering separation, the off-sphere index, and the §3.8 never-imply rules, as binding acceptance criteria for any later build.
5. **Adopt the epistemic pipeline**: graph content reaches the baselines only through reviewed, versioned baseline amendments with forward-only effect; the placement rule of §5.7 as an architectural constraint, not a guideline.
6. **Adopt the population plan and its phasing**: Glottolog pinned as the classification skeleton authority; the batch sequence B0–B6; the three programs at dossier depth; the rest of the census at skeleton depth rising by batch; and the §6.7 verification pass as the gate every batch must clear.
7. **Name the custodians**: who reviews population batches, who adjudicates quarantined items, and who signs a graph release as fit for baseline export.
8. **Fix the graph's home and release cadence**: the repository package that will hold the canonical streams and ledger, and how often authority refreshes (beginning with Glottolog) are taken.

Until those decisions are made, the World Language Graph stands as this design: a specified architecture, three worked examples drawn from the filed record, and no populated content.
